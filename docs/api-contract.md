## 1. General rules

| Rule | Detail |
|---|---|
| Base path | `/api/v1/` |
| Format | JSON in, JSON out. `Content-Type: application/json` |
| Max body | 256 KB (`PAYLOAD_TOO_LARGE` above that) |
| IDs | UUIDs generated by the server |
| Time | ISO 8601 UTC, e.g. `2026-11-12T09:30:00.123456Z` |
| Request ID | Every response has an `X-Request-ID` header (server-generated) |
| Unknown fields | Rejected with `VALIDATION_ERROR` |
| Trailing slash | Required on every path (Django convention) |

## 2. Authentication

### 2.1 Humans (admin, operator, viewer): session cookie + CSRF

1. `GET /api/v1/auth/csrf/` sets the `csrftoken` cookie.
2. `POST /api/v1/auth/login/` with the header `X-CSRFToken: <csrftoken value>`.
   On success the server sets `fogtrust_session` (HttpOnly, SameSite=Strict) and rotates the CSRF token.
3. Every later POST, PUT, PATCH and DELETE sends `X-CSRFToken`.
4. The session expires after **30 minutes of inactivity**, **8 hours after login** however active it is,
   or when the browser closes. A request with an expired session gets `401 AUTH_SESSION_EXPIRED`
   (no session cookie at all gives `401 AUTH_REQUIRED`); the dashboard should send the user to login.

### 2.2 Edge nodes: signed requests (no cookies, no passwords) — *Proposed by M1, owned by M2*

Every node request after enrollment carries:

| Header | Value |
|---|---|
| `X-Node-Id` | Node UUID received at enrollment |
| `X-Node-Timestamp` | Unix time in seconds |
| `X-Node-Nonce` | 16 random bytes, hex (32 chars) |
| `X-Node-Signature` | base64 Ed25519 signature of the string below |

```
string_to_sign = METHOD + "\n" + PATH + "\n" + TIMESTAMP + "\n" + NONCE + "\n" + hex(SHA-256(body))
```

Check order on the server (each failure is logged with its own code):
1. headers present → else `NODE_SIGNATURE_MISSING`
2. node exists → else `NODE_UNKNOWN`
3. node active → else `NODE_REVOKED`
4. signature valid with the stored public key → else `NODE_SIGNATURE_INVALID`
5. timestamp within window → else `HEARTBEAT_STALE`
6. nonce unused → else `HEARTBEAT_REPLAYED`

Heartbeat only, after step 6 (the counter is in the JSON body, which the generic check does not read):
7. body has exactly the agreed fields and types → else `MALFORMED_REQUEST` (not JSON) or `VALIDATION_ERROR`
8. counter greater than the node's last counter → else `HEARTBEAT_COUNTER_REGRESSED`

Before step 1, a body over the endpoint's limit is refused with `PAYLOAD_TOO_LARGE` (heartbeat 2 KB, result about 64 KB).

Rules that make the scheme unambiguous (added in 0.2):
- `PATH` is the request target as sent, **including the `?query`** when there is one (Django: `request.get_full_path()`).
- The hash is over the **raw body bytes**. The server reads `request.body` before DRF parses `request.data`.
- Only an absent or empty header is `NODE_SIGNATURE_MISSING`. A malformed timestamp, nonce or signature is `NODE_SIGNATURE_INVALID`, reported at step 4.
- A state change happens only after the checks that precede it: steps 1 to 4 touch nothing, and the counter moves only when every check has passed. A nonce is remembered once step 6 passes, so a request that fails step 7 or 8 still burns its nonce (harmless: an honest node never reuses one).
- Nonce and counter updates must be atomic (`unique (node, nonce)`; `UPDATE ... WHERE last_counter < new`). Check-then-store is a race.
- The nonce is kept until `timestamp + timestamp_window_s`, then purged.
- The client sees the generic **message** from `errors.py`, but the `code` in the response body is the specific one (`NODE_UNKNOWN` and `NODE_SIGNATURE_INVALID` are both 401, `NODE_REVOKED` is 403). A caller who already holds a node id can therefore learn whether it exists or is revoked. Node ids are random UUIDs, so this is an accepted risk (`threat-model/crypto-engine.md`, CR-7); the full reason also goes to the audit log and the Decision.
- Every header value must be in canonical form, so one request has exactly one valid spelling: `X-Node-Id` is a lower-case hyphenated UUID, `X-Node-Timestamp` is a decimal integer without leading zeros, `X-Node-Signature` is the canonical base64 of 64 bytes. Anything else is refused (`NODE_UNKNOWN` for the id, `NODE_SIGNATURE_INVALID` for the others).
- A view should compare `Content-Length` with the endpoint's limit (`declared_length_too_large`) and refuse before reading the body.

Node endpoints do not use session authentication, so CSRF does not apply to them.

| Capability | admin | operator | viewer | node |

| Export sanitized report | ✓ | ✓ | | |

| Change policy (thresholds, weights) | ✓ | | | |

| Enroll (with a token) | | | | ✓ |
| Send heartbeat, fetch assigned task, submit result | | | | ✓ |

The server enforces this table with DRF permission classes. Any denied request returns
`403 PERMISSION_DENIED` with the generic message "Access denied." and writes an
`access.denied` audit event.

## 4. Response shapes

### 4.1 Success

A single object is returned as-is. Lists are paginated:

```json
{
  "count": 42,
  "next": "/api/v1/nodes/?page=2",
  "previous": null,
  "results": [ ... ]
}
```

Query parameters for lists: `page` (default 1), `page_size` (1 to 100, default 25), plus the
filters listed per endpoint.

### 4.2 Error (every endpoint, every failure)

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The request contains invalid fields.",
    "request_id": "0b6f4d2a-8c1e-4f3b-9a2d-5e6f7a8b9c0d",
    "details": { "fields": { "capacity": ["Ensure this value is less than or equal to 100."] } }
  }
}
```

- `code` is stable and listed in section 6. The frontend switches on `code`, never on `message`.
- `details` is optional and only ever contains safe information.
- Stack traces, SQL, file paths, keys and user input are never included.

```json
// request
{"username": "operator1", "password": "••••••••••"}

// 200
{"user": {"username": "operator1", "role": "operator"}, "session_expires_in": 1800}

// 401 — same response whether the username exists or not
{"error": {"code": "AUTH_INVALID_CREDENTIALS", "message": "Invalid username or password.", "request_id": "..."}}

// 429 after 5 attempts per minute from one client
{"error": {"code": "RATE_LIMITED", "message": "Too many requests. Try again later.", "request_id": "...",
           "details": {"retry_after_seconds": 42}}}
```

**GET `/auth/me/`**

```json
// 200
{"username": "operator1", "role": "operator",
 "permissions": ["decisions.view", "nodes.view", "policy.view", "reports.export", "results.view",

```

Permission names come from `CAPABILITIES` in `backend/accounts/permissions.py`, the single source of
truth for section 3. Server code protects a view with `permission_classes = [require("nodes.revoke")]`.

`permissions` lets the dashboard hide controls the user cannot use. It is a convenience only;
the server still checks every request.

**POST `/enrollment-tokens/`**

```json
// request
{"label": "gateway in lab 2", "expires_in_minutes": 15}

// 201 — the raw token appears only in this response
{"id": "c1d2...", "label": "gateway in lab 2", "token": "q8Zr...43 chars...", "expires_at": "2026-11-19T10:19:12Z"}
```

**POST `/nodes/enroll/`**

The node proves it owns the private key by signing the enrollment message (proof of possession):

```
proof = Ed25519_sign(private_key, "fogtrust-enroll-v1\n" + token + "\n" + name + "\n" + public_key)
```

```json
// request
{
  "enrollment_token": "q8Zr...",
  "name": "gateway-03",
  "public_key": "base64 of the raw 32-byte Ed25519 key (44 characters)",
  "capacity": 4,
  "proof": "base64 of 64-byte signature"
}

// 201
{"node_id": "a7f3c2d1-...", "name": "gateway-03", "status": "active",
 "key_fingerprint": "5e88...", "enrolled_at": "2026-11-19T10:05:00Z"}
```

| Failure | Code returned to client | Code in audit log | HTTP |
|---|---|---|---|
| Token unknown or cancelled | `ENROLL_TOKEN_INVALID` | `ENROLL_TOKEN_INVALID` | 401 |
| Token expired | `ENROLL_TOKEN_INVALID` | `ENROLL_TOKEN_EXPIRED` | 401 |
| Token already used | `ENROLL_TOKEN_INVALID` | `ENROLL_TOKEN_USED` | 401 |
| Proof signature invalid | `ENROLL_PROOF_INVALID` | `ENROLL_PROOF_INVALID` | 401 |
| Key not a valid Ed25519 key | `ENROLL_KEY_INVALID` | `ENROLL_KEY_INVALID` | 400 |
| Key already belongs to another node | `ENROLL_KEY_IN_USE` | `ENROLL_KEY_IN_USE` | 409 |
| Name already taken | `NODE_NAME_TAKEN` | `NODE_NAME_TAKEN` | 409 |

All token failures look identical to the client, so an attacker cannot tell a real-but-used
token from a made-up one. The precise reason is recorded in the audit event's `reason_code`,
which is what the T1 tests and the admin's evidence view check.

Order of checks: validate body → token → proof of possession → key unused → name unused →
create node and mark token used in **one transaction**.

**GET `/nodes/{id}/`**

```json
{
  "id": "a7f3c2d1-...", "name": "gateway-03", "status": "active",
  "key_fingerprint": "5e88...", "capacity": 4, "current_load": 1, "trust_score": 86,
  "last_seen_at": "2026-11-19T10:20:31Z", "enrolled_at": "2026-11-19T10:05:00Z",
  "revoked_at": null, "revoke_reason": null
}
```

The full public key is not returned to viewers (the fingerprint is enough to identify it).

**POST `/nodes/{id}/revoke/`** — high-impact action, needs confirmation

```json
// request: confirm_name must equal the node's name
{"reason": "3 integrity failures in 10 minutes", "confirm_name": "gateway-03"}

// 200
{"id": "a7f3c2d1-...", "status": "revoked", "revoked_at": "2026-11-19T10:31:00Z",
 "revoked_by": "admin1", "revoke_reason": "3 integrity failures in 10 minutes"}
```

| Failure | Code | HTTP |
|---|---|---|
| Not an admin | `PERMISSION_DENIED` | 403 |
| `confirm_name` missing or different | `CONFIRMATION_REQUIRED` | 400 |
| Already revoked | `NODE_ALREADY_REVOKED` | 409 |
| Reason shorter than 10 chars | `VALIDATION_ERROR` | 400 |

After revocation: heartbeats → `NODE_REVOKED`, no new task assignments, and in-flight tasks
on that node are returned to the queue (Member 3).

### 5.7 Results — Member 2 (*Proposed*)

| Method | Path | Auth | Wk | Purpose |
|---|---|---|---|---|
| POST | `/node-api/tasks/{id}/result/` | signed node, assigned to that task | 3 | FR-5 |
| GET | `/tasks/{id}/result/` | operator, admin | 3 | Decrypted summary and integrity status |

```json
// POST /node-api/tasks/{id}/result/ body (a normal signed node request per 2.2)
{
  "ephemeral_public_key": "base64, 44 chars (X25519, 32 bytes)",
  "nonce": "base64, 16 chars (12 bytes)",
  "ciphertext": "base64, AES-256-GCM output (data + 16-byte tag), at most 65536 chars"
}
// 200
{"accepted": true}
```

- The node encrypts to the server's long-term X25519 public key (ECDH with a new ephemeral key per result, HKDF-SHA256, AES-256-GCM).
  The associated data binds the ciphertext to `node_id` and `task_id`.
- There is no separate envelope signature: the request signature (2.2) covers the body hash, so it already covers the ciphertext.
- Check order: size, steps 1 to 6 of 2.2, task assigned to this node (else `RESULT_NOT_ASSIGNED`), JSON parse, envelope fields
  (`VALIDATION_ERROR`), GCM tag (`RESULT_INTEGRITY_FAILED`). The server stores `plaintext_sha256`, never the plaintext where avoidable.
- A result for a task that already has one is the caller's `TASK_INVALID_STATE`.
- **Open for Member 1 (proposal):** the server's X25519 public key is returned in the enrollment response as `server_public_key`
  (section 5.4); the private key is loaded from a 0600 file named by `FOGTRUST_RESULT_KEY_FILE` and kept out of git.
